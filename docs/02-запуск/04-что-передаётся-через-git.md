# Что передаётся через Git и почему некоторых файлов нет

[Полная инструкция для нового компьютера](../../ЗАПУСК.md).

`.gitignore` — список файлов, которые Git не должен добавлять как новые файлы репозитория. Он не удаляет файлы с диска, не скрывает их в проводнике и не ограничивает доступ к уже опубликованным файлам. [Официальное описание Git](https://git-scm.com/docs/gitignore).

## Что передаётся другому человеку

- `backend/app/`, `backend/tests/`, оба `requirements*.txt` и команды запуска.
- `frontend/` вместе с HTML, CSS, JavaScript и готовыми изображениями в `assets/img/`.
- Общие инструменты `scripts/`, корневой `START.cmd`.
- `backend/.env.example` и `deploy/.env.production.example` — примеры без личных значений автора.
- Документация, Dockerfile, compose-файлы, конфигурации размещения.
- `.gitignore` и `.gitattributes` — сами правила тоже сохраняются в Git.

## Что не передаётся

| Правило | Что исключено | Причина |
|---|---|---|
| `.venv/`, `venv/` | Локальные библиотеки и интерпретатор | Создаются заново на каждом компьютере |
| `.env`, `.env.*`, кроме примеров | Личные переменные, настройки и секреты | Новый `.env` создаётся из опубликованного шаблона |
| `backend/data/`, `*.db`, `*.sqlite*` по указанным шаблонам | Рабочая база | Данные автора не должны попадать в код; новая база создаётся автоматически |
| `__pycache__/`, `.pytest_cache/`, прочие кэши | Результаты работы инструментов | Не являются исходниками |
| `tmp/`, `temp/`, `*.log`, резервные копии | Временные файлы | Не нужны для запуска |
| `assets-src/` | Оригиналы изображений до подготовки | Готовые ресурсы сайта остаются в `frontend/assets/img/` |
| `.idea/`, `.vscode/` | Локальные настройки редакторов и инструментов | Не нужны другому компьютеру |
| `*.key`, `*.pem`, `*.p12`, `*.pfx` | Локальные ключи и сертификаты | Не являются частью исходников приложения |

Исключения `!.env.example` и `!.env.*.example` сохраняют шаблоны настроек, хотя общий шаблон `.env.*` скрывает реальные конфигурации.

## Что создаст первый запуск

```text
Исходники из Git
    → START.cmd
    → backend/.venv + установка requirements.txt
    → backend/.env из backend/.env.example
    → backend/data/barber.db + демо-данные
    → сайт localhost:5500 и API localhost:8000
```

Если человек скачал проект без базы, он получит новую демонстрационную базу. Это не резервная копия личных данных автора.

## Git и ZIP — разница

ZIP, сформированный GitHub из репозитория, содержит опубликованные файлы репозитория. Если просто упаковать всю локальную папку через проводник, `.gitignore` автоматически не применяется: внутрь такого ZIP могут попасть `.env`, база и `.venv`. Перед ручной отправкой проверяйте состав архива или формируйте его из Git.

После создания коммита можно получить архив только из его файлов:

```powershell
git archive --format=zip --output=..\BlindBarber-source.zip HEAD
```

Эта команда требует Git-репозиторий с коммитом. В обычной папке, скачанной как ZIP, история Git может отсутствовать.

## Как проверить правила

Команды выполняются в корне **Git-репозитория**:

```powershell
git check-ignore -v backend/.env
git check-ignore -v backend/.venv/Scripts/python.exe
git status --short --ignored
```

`check-ignore` показывает правило, которое исключает путь. Примеры `.env.example`, исходники, изображения и документация не должны оказаться среди исключённых.

Файл `.gitattributes` задаёт CRLF для Windows-команд `.cmd` / `.ps1` и LF для исходников и shell-скриптов. Это помогает сохранить ожидаемые переводы строк при checkout на разных ОС.

## Если файл уже был закоммичен

Добавление правила не прекращает отслеживание уже закоммиченного файла. Сначала проверьте:

```powershell
git ls-files backend/.env backend/data backend/.venv
```

Если это ваши локальные файлы, которые нужно убрать только из следующих коммитов, можно выполнить адресные команды:

```powershell
git rm --cached --ignore-unmatch backend/.env .env
git rm -r --cached --ignore-unmatch backend/.venv backend/data tmp assets-src
git status
```

`--cached` удаляет из индекса Git, сохраняя локальные файлы. Просмотрите результат и затем создайте коммит. Это не очищает старую историю: реальный пароль, ранее попавший в опубликованный коммит, нужно заменить.

В исходной рабочей папке при этой настройке Git-репозиторий не был инициализирован; удалять что-либо из индекса не потребовалось. Создание репозитория, коммита и загрузка на GitHub — отдельные действия.

Первый START.cmd установил зависимости и самостоятельно создал все три компонента; сайт, API и изображения работали. Созданные локальные файлы не изменили `git status`.
