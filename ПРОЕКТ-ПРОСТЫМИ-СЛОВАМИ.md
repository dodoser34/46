## 1. Что это за проект

**Blind Barber** — сайт сети барбершопов (мужских парикмахерских) в Казахстане:
6 барбершопов в трёх городах (Алматы, Астана, Костанай), 12 мастеров, 8 услуг и 10 товаров в магазине.

Какую проблему решает. Обычно, чтобы подстричься, нужно позвонить, дождаться ответа
администратора и подобрать время голосом: «а в три можно? нет? а в пять?». Сайт убирает этот шаг:

- человек сам видит, какое время у мастера **свободно прямо сейчас**, и записывается в пару кликов;
- барбершоп получает запись без звонка и видит все записи в панели администратора;
- заодно можно купить средства для ухода (воск, масло для бороды и т.д.) в интернет-магазине.

Это дипломный проект: полноценный рабочий сайт с сервером, базой данных, личным кабинетом,
админкой, автотестами и готовыми настройками для размещения в интернете.

## 2. Из каких частей состоит

Любой современный сайт — это три части. Проще всего представить ресторан:

```
  ПОСЕТИТЕЛЬ
      │  смотрит, нажимает кнопки
      ▼
┌─────────────────────┐
│  ФРОНТЕНД  (зал)    │  то, что видно в браузере: страницы, кнопки, фото
│  HTML + CSS + JS    │  папка frontend/
└─────────┬───────────┘
          │  запросы через API («официант»): «дай свободное время», «запиши меня»
          ▼
┌─────────────────────┐
│  БЭКЕНД   (кухня)   │  сервер на Python: проверяет и выполняет действия
│  Python + FastAPI   │  папка backend/
└─────────┬───────────┘
          │  читает и записывает
          ▼
┌─────────────────────┐
│  БАЗА ДАННЫХ (склад)│  все барбершопы, мастера, записи, заказы, пользователи
│  SQLite             │  файл backend/data/barber.db
└─────────────────────┘
```

- **Фронтенд** только показывает и спрашивает. Он ничего не решает сам.
- **Бэкенд** — главный. Он проверяет каждое действие: свободно ли время, есть ли товар,
  правильный ли пароль, админ ли это.
- **База данных** хранит всё, чтобы после перезапуска ничего не пропало.

Подробнее — [общая схема](docs/03-устройство/01-общая-схема.md).

## 3. Что умеет сайт

| Страница | Что на ней можно сделать |
|---|---|
| **Главная** | Найти барбершоп по городу и услуге, посмотреть популярные барбершопы и услуги, подписаться на новости |
| **Барбершопы** | Список с фильтром по городу, поиском, «Открыто сейчас», «Рядом со мной» (по геолокации), избранное |
| **Страница барбершопа** | Фотогалерея, услуги с ценами, мастера, отзывы с оценками, адрес и часы работы |
| **Мастер** | Профиль, опыт, портфолио работ, отзывы, кнопка записи к нему |
| **Запись** | Пошаговая запись: услуга → мастер → дата и время → подтверждение |
| **Услуги** | Все услуги с ценой и длительностью |
| **Магазин** | Товары по категориям, поиск, сортировка, карточка товара |
| **Корзина** | Изменить количество, оформить заказ (самовывоз или курьер) |
| **О нас** | История бренда |
| **Вход / регистрация** | Создать аккаунт или войти |
| **Личный кабинет** | Профиль, мои записи (с отменой), мои заказы, избранное |
| **Админка** | Сводка, все записи и заказы, смена статусов |

Три вида пользователей:

- **гость** — может всё смотреть, записаться и сделать заказ без регистрации;
- **клиент** (зарегистрирован) — плюс личный кабинет, избранное, отзывы, отмена записи;
- **администратор** — плюс панель управления всеми записями и заказами.

Для показа есть готовые аккаунты: `demo@barber.kz / demo123` (клиент) и `admin@barber.kz / admin123` (админ).

Дизайн: тёмный фон, медные акценты, крупные заголовки с засечками — как в дорогом барбершопе.
Сайт подстраивается под телефон, а анимации (плавное появление блоков, эффект глубины на главном
экране) выключаются сами, если в системе включено «уменьшить движение».
Подробнее — [страницы](docs/04-сайт-фронтенд/01-страницы-сайта.md), [дизайн](docs/04-сайт-фронтенд/03-дизайн-и-адаптив.md), [анимации](docs/04-сайт-фронтенд/04-анимации-и-эффекты.md).

## 4. Как работает запись к мастеру — по шагам

Это главная функция сайта, поэтому разберём её подробно.

**Шаг 1. Человек выбирает барбершоп и услугу.**
Страница `booking.html` просит у сервера список барбершопов и услуг (`GET /api/barbershops`,
`GET /api/services`) и показывает их.

**Шаг 2. Выбирает мастера.**
Показываются мастера именно этого барбершопа.

**Шаг 3. Выбирает дату и время.**
Страница спрашивает у сервера: «какое время свободно у мастера №3 на 25 октября для стрижки?»
(`GET /api/masters/3/slots?date=2026-10-25&service_id=1`).

Сервер считает это так (файл `backend/app/modules/booking/service.py`, функция `compute_slots`):

1. берёт часы работы барбершопа, например 10:00–22:00;
2. нарезает их по часу: 10:00, 11:00, 12:00…;
3. для каждого времени проверяет три вещи:
   - услуга **успевает закончиться** до закрытия (стрижка+борода 1,5 часа в 21:00 уже не поместится);
   - время **не пересекается** с уже существующими записями этого мастера;
   - если это сегодня — время **ещё не прошло** (и до него больше 15 минут);
4. возвращает список: `13:00 — свободно`, `14:00 — занято` и т.д.

Занятые часы на странице видны, но нажать на них нельзя.

**Шаг 4. Подтверждение.**
Человек вводит имя и телефон и нажимает «Записаться». Сайт отправляет `POST /api/bookings`.

Сервер **проверяет всё заново**, не доверяя странице:

- существуют ли такой барбершоп, мастер и услуга;
- работает ли мастер в этом барбершопе;
- дата не в прошлом и не дальше чем через 30 дней;
- время всё ещё свободно.

Если всё хорошо — запись сохраняется в базу, человек видит «Вы записаны» с праздничной анимацией.
Если за это время кто-то успел занять тот же час — сервер отвечает «Это время уже занято,
выберите другое» (код 409), и страница предлагает выбрать другое.

**Как сайт не даёт записать двух человек на одно время** — тут три уровня защиты:

1. **Проверка свободного времени** (выше).
2. **Блокировка мастера**: пока сервер проверяет и сохраняет одну запись к мастеру, вторая
   запись к тому же мастеру ждёт своей очереди. Иначе два запроса, пришедшие в одну и ту же
   долю секунды, могли бы оба увидеть «свободно».
3. **Правило в самой базе данных** (уникальный индекс): у мастера не может быть двух активных
   записей на одну дату и время. Даже если бы в коде была ошибка, база откажется сохранять дубль.

Это проверено автотестами: два запроса на пересекающееся время отправляются одновременно,
и сохраняется только один. То же самое проверено для последней единицы товара в магазине.

Подробнее — [логика записи](docs/05-сервер-бэкенд/03-логика-записи.md).

## 5. Как работает заказ в магазине

1. Человек нажимает «В корзину». Корзина хранится **в браузере** (localStorage) — в ней только
   номера товаров и количество, **без цен**.
2. На странице корзины человек выбирает самовывоз или курьера и оформляет заказ (`POST /api/orders`).
3. Сервер **сам** берёт цены из базы и пересчитывает сумму. Цены, которые видны в браузере,
   ни на что не влияют.
4. Сервер проверяет остаток и сразу резервирует товар: «уменьши остаток на 2, **только если**
   на складе есть хотя бы 2». Поэтому два покупателя не могут купить одну последнюю банку воска.
5. Доставка курьером — 1 500 ₸, при заказе от 30 000 ₸ — бесплатно. Не больше 20 штук одного товара.
6. Если администратор отменяет заказ, товары возвращаются на склад.

**Почему цены не берутся из браузера.** Всё, что лежит в браузере, человек может изменить
(это несложно сделать через инструменты разработчика). Если бы сервер верил цене из корзины,
можно было бы «купить» шампунь за 1 тенге. Поэтому правило проекта: **браузер только просит,
сервер решает**.

Подробнее — [магазин и заказы](docs/05-сервер-бэкенд/04-магазин-и-заказы.md).

## 6. Вход, пароли и безопасность

**Пароли не хранятся.** В базе лежит не пароль, а его «отпечаток» (хэш). Из отпечатка пароль
восстановить нельзя. Когда человек входит, сервер делает отпечаток от введённого пароля и сравнивает
два отпечатка. Используется алгоритм PBKDF2: к паролю добавляется случайная **соль**, и отпечаток
считается 200 000 раз подряд — так подбор пароля перебором становится очень долгим.

**Токен — пропуск.** После входа сервер выдаёт длинную случайную строку — токен. Браузер прикладывает
его к каждому запросу, и сервер понимает, кто это. Токен действует 30 дней, при выходе удаляется.

**Защита от подбора пароля.** Если за 15 минут было 8 неудачных попыток входа, сервер временно
перестаёт принимать попытки для этого email с этого адреса (код 429) и пишет, сколько минут подождать.

**Права.** Каждый адрес API сам проверяет, можно ли этому человеку: чужие записи не видны,
в админку пускают только администратора (иначе код 403).

**Защита от вредного текста (XSS).** Если кто-то напишет в отзыве `<script>…</script>`, сайт покажет
это как обычный текст, а не выполнит. Для этого весь текст от пользователей проходит через функцию
`esc()` («экранирование»).

**Защита базы (SQL-инъекции).** Запросы к базе строятся через библиотеку SQLAlchemy, которая не даёт
подставить в запрос «чужую команду» из поля ввода.

**Проверка данных.** Телефон, email, имя, количество товара проверяются на сервере (библиотека Pydantic).

**Нельзя забыть пароль администратора.** Если запустить сайт в режиме «для интернета» со стандартным
паролем `admin123`, сервер откажется стартовать и попросит задать свой пароль.

Подробнее — [безопасность](docs/05-сервер-бэкенд/05-безопасность.md).

## 8. Почему сделано именно так

На защите чаще всего спрашивают не «что», а «почему». Вот главные решения и их причины.

**Почему сайт и сервер разделены.**
Так делают все серьёзные сайты. Сервер можно проверить отдельно от внешнего вида, страницы
можно перерисовать, не трогая логику, а когда-нибудь подключить мобильное приложение
к тому же API.

**Почему сервер на Python и FastAPI.**
Python — один из самых читаемых языков, код похож на английский текст. FastAPI — современный
фреймворк: он сам проверяет входящие данные, сам создаёт страницу документации API (`/docs`)
и работает быстро. Меньше кода — меньше ошибок.

**Почему сайт без фреймворков (без React, Vue и т.п.).**
- Не нужна сборка и установка Node.js: открыл файл — работает.
- Каждую строку можно объяснить: нет «магии» чужой библиотеки.
- Страницы грузятся быстрее: браузеру не нужно скачивать большой фреймворк.
- Для сайта такого размера фреймворк не даёт заметной выгоды.
Код всё равно разбит на модули (ES-модули: `import` / `export`), как в больших проектах.

**Почему база SQLite.**
Ничего не нужно устанавливать: база — это один файл, она создаётся и заполняется сама при первом
запуске. Для показа и проверки это идеально. А для настоящей работы в интернете поддерживается
PostgreSQL: достаточно указать адрес базы в настройке `DATABASE_URL`, код менять не нужно.
Это возможно благодаря SQLAlchemy — она одинаково работает с обеими базами.

**Почему «модульный монолит».**
«Монолит» — одна программа, а не десяток отдельных сервисов: её проще запустить, проверить и разместить.
«Модульный» — внутри код разложен по темам (аккаунты, каталог, запись, магазин, админка), и каждая
тема лежит в своей папке. Нужно поменять что-то в магазине — открываешь только папку `shop`.
Подробнее — [модули](docs/03-устройство/03-модули.md).

**Почему сервер проверяет всё повторно.**
Главное правило безопасности: **не доверять клиенту**. Страница может быть подделана, запрос можно
отправить в обход сайта. Поэтому цены, остатки, свободное время и права проверяет только сервер.

**Почему записи и заказы не удаляются, а получают статус.**
Статусы: новая → подтверждена → выполнена или отменена. История сохраняется: видно, кто отменил,
можно восстановить по ошибке отменённое, а отчёт по выполненным заказам считается честно.

**Почему время записи кратно часу.**
Так проще и клиенту, и мастеру: расписание читается с одного взгляда. Шаг задан одной константой
`SLOT_STEP = 60` — если барбершопу нужен шаг 30 минут, меняется одно число.

**Почему при разработке два сервера (5500 и 8000).**
Так видно, что фронтенд и бэкенд — действительно отдельные части. Сервер сайта на порту 5500
раздаёт страницы и пересылает все запросы `/api/…` серверу Python на 8000. Браузер думает, что
говорит с одним сайтом, поэтому не нужны дополнительные настройки (CORS). В интернете
работает один сервер, который раздаёт и страницы, и API, — так проще и дешевле.

**Почему фото главного экрана из слоёв.**
Фон, человек и детали лежат отдельными картинками. При прокрутке они двигаются с разной скоростью —
получается эффект глубины (параллакс), а огромное слово STYLE оказывается «за» человеком.

**Почему есть отдельное демо для GitHub Pages.**
GitHub Pages бесплатно показывает сайты, но не умеет запускать Python. Поэтому для него собирается
особая версия, где «сервер» имитируется прямо в браузере. Так сайт можно показать по ссылке
без оплаты хостинга. Настоящая версия с сервером и базой остаётся основной.

## 9. Как это запускается

Нужен только **Python 3.11 или новее** (при установке поставить галочку «Add Python to PATH»).

1. Двойной щелчок по `START.cmd`.
2. Первый раз он сам создаст папку `.venv` и скачает библиотеки — нужен интернет, 1–3 минуты.
3. Он сам создаст базу и заполнит её демо-данными.
4. Когда появится **ГОТОВО**, открыть в браузере http://localhost:5500.
5. Остановить — `Ctrl+C` в окне или просто закрыть окно.

Что происходит внутри `START.cmd`: он вызывает `scripts/dev/launcher.py`, который запускает
два сервера — сайт (порт 5500) и API (порт 8000) — и следит, чтобы оба работали.

Если что-то не так — [ЗАПУСК.md](ЗАПУСК.md) и [если что-то не работает](docs/02-запуск/03-если-что-то-не-работает.md).

## 10. Как проверено, что всё работает

- **62 автотеста** (`backend/tests/`), все проходят. Они проверяют: регистрацию и вход, фильтры,
  свободное время, защиту от двойной записи (в том числе при одновременных запросах), отмену,
  заказы с серверными ценами и остатками, доставку, права администратора, ошибки 404,
  запуск проекта из разных папок и сборку демо.
- **Ручная проверка** в браузере на компьютере и на ширине телефона по
  [чек-листу](docs/07-тестирование/02-ручная-проверка.md).

Запустить автотесты:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/test.ps1
```

## 11. Как выложить в интернет

«Выложить в интернет» называется **деплой**. Всё для него уже подготовлено, нужно только выбрать место:

| Способ | Что это | Файл |
|---|---|---|
| **Render** | Хостинг: подключил репозиторий GitHub — сайт и база PostgreSQL создались сами | `render.yaml` |
| **Docker** | Проект упакован в «контейнер», который одинаково запускается на любом сервере | `Dockerfile`, `docker-compose.yml` |
| **Свой сервер (VPS)** | Одна команда ставит всё: сайт, nginx, HTTPS-сертификат, ежедневные копии базы | `deploy/vps/install.sh` |
| **GitHub Pages** | Бесплатная демо-версия без сервера, по ссылке | `.github/workflows/pages.yml` |

Пошагово — [инструкция по деплою](docs/08-деплой/02-инструкция-по-деплою.md).

## 12. Рассказ на 2 минуты

Можно выучить почти дословно:

> Мой проект — Blind Barber, веб-сервис для сети барбершопов. Он решает проблему записи по телефону:
> клиент сам видит свободное время мастера и записывается онлайн, а ещё может купить средства
> для ухода в интернет-магазине.
>
> Система клиент-серверная. Клиентская часть — сайт на HTML, CSS и JavaScript без фреймворков,
> адаптированный под телефоны. Серверная часть — на Python с фреймворком FastAPI. Данные хранятся
> в базе SQLite, а для размещения в интернете поддерживается PostgreSQL. Сайт и сервер общаются
> через REST API в формате JSON.
>
> Главная логика — расчёт свободного времени: сервер учитывает часы работы барбершопа,
> длительность услуги и уже существующие записи. От двойной записи на одно время защищают
> три уровня: проверка слотов, блокировка мастера на время сохранения и уникальное правило
> в самой базе.
>
> В магазине цены и остатки всегда берутся с сервера, а товар резервируется сразу при заказе,
> поэтому нельзя ни подменить цену, ни купить больше, чем есть.
>
> Пароли хранятся только в виде хэша с солью, вход защищён от подбора, права проверяются
> на каждом запросе, а пользовательский текст экранируется от XSS-атак.
>
> Есть личный кабинет и панель администратора. Проект покрыт 62 автотестами и подготовлен
> к размещению через Docker, Render или собственный сервер.

Полный план выступления — [план](docs/09-защита-диплома/01-план-выступления.md),
сценарий показа — [демонстрация](docs/09-защита-диплома/03-сценарий-демонстрации.md).

## 13. Короткие ответы на частые вопросы

**Что такое фронтенд и бэкенд?**
Фронтенд — то, что человек видит в браузере. Бэкенд — сервер, который хранит данные и проверяет действия.

**Что такое API?**
Набор адресов, через которые сайт просит сервер что-то дать или сделать. Например, `/api/bookings` — создать запись.

**Что такое база данных и какая у вас?**
Хранилище в виде таблиц. У нас SQLite — база в одном файле; на хостинге можно PostgreSQL.

**Что будет, если два человека одновременно запишутся на одно время?**
Сохранится только одна запись, второй человек увидит «время уже занято». Защита в трёх местах, и это проверено тестом.

**Можно ли изменить цену в корзине и купить дешевле?**
Нет. Корзина хранит только номера товаров и количество, цену сервер берёт из базы.

**Как хранятся пароли?**
Не хранятся. Хранится хэш (отпечаток) с солью, из которого пароль не восстановить.

**Почему без React?**
Сайт небольшой, без фреймворка он быстрее, не требует сборки, и каждую строку можно объяснить.

**Почему Python?**
Читаемый язык, а FastAPI сам проверяет данные и делает документацию API.

**Как проверяли?**
62 автотеста и ручная проверка по чек-листу на компьютере и телефоне.

**Что можно добавить дальше?**
Онлайн-оплату, SMS или email-напоминания о записи, мобильное приложение на том же API,
выбор шага времени для каждого барбершопа.

Больше вопросов (около 60) с ответами — [вопросы и ответы](docs/09-защита-диплома/02-вопросы-и-ответы.md).
